# ganluo · 需求文档

> 情侣私密日常记录小程序
> 版本 v0.1（初稿，待确认） · 2026-10-13

---

## 一、产品定位

一个**只服务于两个人**的私密日常记录工具。用户通过微信一键登录，与另一半互相绑定后，
可以看到彼此每天的心情、一日三餐和留给对方的话。

核心诉求是**"被看见"**——不是社交，不是记账，而是让两个人即使不在一起，
也能知道对方今天过得怎么样、吃了什么、开不开心。

产品原则：

| 原则 | 说明 |
|---|---|
| 私密 | 数据只在绑定的两个人之间可见，不对外泄露，不被微信索引 |
| 轻量 | 记录动作不超过 2 步，不强迫填写 |
| 双向 | 主页同时呈现「我」和「TA」两个对等板块，不分主次 |
| 陪伴感 | 视觉温暖柔和，用「在一起第 N 天」等细节强化关系感 |

## 二、角色与关系模型

- **普通用户**：所有登录用户，默认角色，无管理员后台。
- **关系**：一对一的绑定关系（一夫一妻制）。一个人同时只能绑定一个伴侣。
  - 未绑定：只能记录和查看自己的内容，看不到对方板块
  - 已绑定：主页出现「TA」板块，可以互相查看心情与三餐，可以互相留言
  - 解除绑定：**对方的数据立即不可见**，双方此后可以各自绑定其他人

### 数据可见性规则（重要）

**解除绑定后，双方都只能看到自己的数据，看不到对方的任何内容。**

| 数据类型 | 解绑后 | 说明 |
|---|---|---|
| 对方的心情日记 | ❌ 不可见 | 主页「TA」板块消失，直接调接口也会返回 403 |
| 对方的三餐报备 | ❌ 不可见 | 同上 |
| **对方发来的留言** | ❌ **不可见** | 收件箱只展示「当前伴侣」发来的留言，解绑后直接为空 |
| 自己发出去的留言 | ✅ 可见 | 属于"自己的数据"，发件箱完整保留 |
| 自己记录的全部内容 | ✅ 可见 | 自己写的心情、三餐，一条都不会丢 |

> ⚠️ 注意区分「**不可见**」和「**被删除**」：
> 解绑**不会删除任何数据**，记录仍完整保留在数据库里，只是不再向对方展示。
> 只有在双方**重新互相绑定**之后，对方的数据才会重新可见。

**用户 ID**：每个用户注册时自动生成一个 8 位邀请码（如 `7K3M9QX2`），
去掉容易看错的 `I O 0 1`。这就是用户口中"对方的用户ID"，凭它发起绑定。
（不使用自增数字 ID，避免用户猜到别人的编号。）

## 三、功能清单

### 3.1 登录

| 项 | 说明 |
|---|---|
| 方式 | 微信一键登录，无手机号、无密码 |
| 流程 | 点「微信一键登录」→ 调 `wx.login` 拿 code → 后端 `code2Session` 换 openid → 查库；没有则自动注册 |
| 首次注册 | 自动分配随机昵称（如"软软的小汤圆"）和 8 位用户 ID，头像留空 |
| 登录态 | 后端签发 JWT，前端存 storage；有效期 7 天，过期后重新登录 |
| 头像昵称 | 登录不强制授权；进入「我的」页面可自行填写昵称和签名 |
| 退出 | 「我的」页面底部，退出后需重新微信登录，**数据不丢失** |

### 3.2 绑定

| 项 | 说明 |
|---|---|
| 发起 | 输入对方 8 位用户 ID → 发送绑定请求 |
| 通知 | 对方进入「我的」页面看到「待处理的请求」，可同意 / 拒绝 |
| 同意 | 双方互为伴侣，记录绑定时间（`bind_at`，可当纪念日） |
| 拒绝 | 请求作废 |
| 撤销 | 发起方可以撤销自己还没被处理的请求 |
| 双向申请 | 如果两人同时向对方发起请求，后发起的一方会自动完成绑定（避免互相等待） |
| 校验 | 不能绑定自己；对方已绑定则提示；自己已绑定则要求先解除 |
| 解除 | 已绑定的「我的」页面有「解除」入口，二次确认后断开。**断开后对方的数据立即不可见**（详见第二节的数据可见性规则） |

### 3.3 主页（「日常」Tab）

主页是核心页面。上半部分是「我」，下半部分是「TA」，**两个板块结构完全一致**，
每个板块包含三个功能块：

#### ① 心情日记

| 项 | 说明 |
|---|---|
| 记录 | 「我」板块点击「＋ 记录」→ 选心情 → 补一句话（可留空） |
| 心情种类 | 8 种：开心 😊 / 幸福 🥰 / 平静 😌 / 兴奋 🤩 / 疲惫 😪 / 难过 😢 / 生气 😠 / 焦虑 😰 |
| 展示 | 每条显示 emoji + 心情名 + 文字 + 时间 |
| 频率 | 一天可以记录多条，全部按时间倒序展示 |
| 权限 | 只能记录自己的；对方的只能看，不能改 |
| 查看历史 | 顶部左右箭头切换日期，可回看任意一天 |

#### ② 三餐报备

| 项 | 说明 |
|---|---|
| 餐次 | 固定四格：早餐 / 午餐 / 晚餐 / 宵夜 |
| 记录 | 点某一格 → 选「拍照/相册」或「只写文字」 |
| 图片 | 每餐最多 9 张，上传到后端；主页格子只显示第一张封面 |
| 文字 | 可留空，但「图片和文字不能同时为空」 |
| 覆盖规则 | 同一天同一餐次只有一条记录，再次提交视为覆盖更新 |
| 权限 | 只能记录自己的；对方的只能看 |
| 查看历史 | 与心情日记共用日期切换 |

#### ③ 留言提醒

| 项 | 说明 |
|---|---|
| 发送 | 只能发给伴侣（未绑定不能发） |
| 内容 | 最多 500 字 |
| 立即送达 | 默认，发送后对方下次打开就能看到 |
| 定时提醒 | 可开关，选日期 + 时间，到点后提醒对方（见下方待确认） |
| 接收 | 「我」板块显示未读条数红点，点「查看」弹出收件箱，打开即全部标记已读。收件箱**只显示当前伴侣**发来的留言，解除绑定后为空 |
| 删除 | 收件箱里可以删除留言 |
| 撤回 | 接口支持发送方删除自己发出的留言 |

### 3.4 个人页（「我的」Tab）

| 区块 | 内容 |
|---|---|
| 我的资料 | 头像 + 昵称 + 个性签名，可直接编辑并保存 |
| 我的用户 ID | 大字号展示 8 位 ID，一键复制，提示"发给 TA" |
| 我的另一半 | 已绑定：显示对方头像昵称 + 绑定日期 + 解除绑定入口 |
| 绑定另一半 | 未绑定：输入框 + 发送绑定请求按钮 |
| 待处理的请求 | 别人发给我的绑定请求，同意 / 拒绝 |
| 我发出的请求 | 我发出去还没被处理的，可撤销 |
| 退出登录 | 底部 |

## 五、数据模型

数据库：MySQL，库名 `ganluo`，字符集 `utf8mb4`。

```
users                    用户
├── id                   主键
├── openid               微信 openid（唯一）
├── nickname / avatar    昵称、头像
├── invite_code          8位用户ID（唯一）
├── signature            个性签名
├── partner_id           伴侣的用户id，NULL = 未绑定
├── bind_at              绑定时间（纪念日）
└── status               1正常 0禁用

bind_requests            绑定请求
├── from_user_id / to_user_id
└── status               0待处理 1已同意 2已拒绝 3已撤销

moods                    心情日记
├── user_id
├── mood_type            8种心情之一
├── content              心情文字，可空
├── mood_date            归属日期（按天查询）
└── created_at

meals                    三餐报备
├── user_id
├── meal_type            breakfast / lunch / dinner / supper
├── content              文字描述，可空
├── images               JSON 数组，图片 URL
├── meal_date            归属日期
└── 唯一键(user_id, meal_type, meal_date)   ← 同一天同一餐只能一条

messages                 留言提醒
├── from_user_id / to_user_id
├── content
├── remind_at            定时提醒时间，NULL = 立即
├── is_read / read_at    已读状态
└── is_notified          定时提醒是否已推送
```

建表脚本：`server/sql/schema.sql`（直接导入即可）。

## 六、接口设计

统一响应格式：`{ "code": 0, "message": "ok", "data": ... }`，`code = 0` 表示成功。
除登录外所有接口需要请求头 `Authorization: Bearer <token>`。

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/auth/login` | 微信登录（code 换 token），首次自动注册 |
| GET | `/api/auth/me` | 当前登录用户信息 |
| GET | `/api/user/me` | 我的资料 + 伴侣信息 |
| PUT | `/api/user/me` | 修改昵称 / 头像 / 签名 |
| GET | `/api/user/search` | 按用户ID查找对方 |
| POST | `/api/bind/apply` | 发起绑定请求 |
| GET | `/api/bind/requests` | 收到 + 发出的绑定请求 |
| POST | `/api/bind/handle` | 同意 / 拒绝绑定 |
| POST | `/api/bind/cancel` | 撤销我发出的请求 |
| POST | `/api/bind/unbind` | 解除绑定 |
| GET | `/api/home` | **主页聚合**：一次返回我和 TA 当天的全部数据 |
| GET | `/api/moods` | 心情列表（按日期或月份） |
| POST | `/api/moods` | 记录心情 |
| PUT | `/api/moods/{id}` | 修改心情 |
| DELETE | `/api/moods/{id}` | 删除心情 |
| GET | `/api/meals` | 三餐列表（按日期） |
| POST | `/api/meals` | 报备一餐 |
| DELETE | `/api/meals/{id}` | 删除某餐 |
| GET | `/api/messages` | 留言列表（收件箱 / 发件箱） |
| POST | `/api/messages` | 发留言（可带定时提醒） |
| POST | `/api/messages/{id}/read` | 标记已读 |
| POST | `/api/messages/read-all` | 全部已读 |
| DELETE | `/api/messages/{id}` | 删除留言 |
| POST | `/api/upload/image` | 上传图片，返回 URL |

> 主页用 `/api/home` 一个聚合接口拿全部数据，避免首屏发 6 个请求。

## 七、技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | **uni-app（Vue3）**，配合 HBuilderX | 一套代码可编译到微信小程序 / App / H5；微信小程序端是**全量支持**；在 HBuilderX 里可直接「运行到微信开发者工具」，不用单独维护另一套工具链 |
| 后端 | PHP 8.2，**自研轻量框架**（无第三方依赖） | 路由 / PDO / JWT / 配置全部手写，只有约 20 个文件，看得懂、改得动 |
| 数据库 | MySQL 8 | 结构化数据，关系简单 |
| 鉴权 | 自签 HS256 JWT | 不引入 composer 包，避免依赖下载问题 |
| 图片 | 存服务器本地 `public/uploads/年-月/` | 先跑通；上线建议换云存储 COS/OSS |
| 密码 | 无 | 全靠微信 openid，不存任何密码 |

> **为什么不用 uni-app x？** uni-app x 用的是 UTS 语言（不是 JS），且按 DCloud 官方文档，
> 它编译到微信小程序是 **Partial（部分支持）** —— 小程序端没有真正的 DOM，UniElement 能力受限，
> 还有基础库版本、virtualHost 等一堆限制。它真正的强项是 **App 端原生渲染**。
> 本项目只要微信小程序，用 uni-app x 是绕远路，所以选 **uni-app（Vue3）**。
